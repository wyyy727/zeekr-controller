## 一、核心门槛：GW3 签名 —— ✅ 已验证（2026-10-16）

| 项 | 说明 | 状态 |
|---|---|---|
| 签名头白名单 | 参与签名的头为 `GW3_SIGNED_HEADERS` 中列出的 11 个，**不是**所有 `x-api*` 头 | ✅ 通过 |
| 签名版本头 | 需发送 `X-API-SIGNATURE-VERSION: 2.0` | ✅ 通过 |
| 待签名串格式 | 头段每行 `name:value\n`（冒号后无空格、行末有换行）；query 段末尾有换行；body 段为 `base64(md5(body))` 且末尾有换行 | ✅ 通过 |
| body 字节一致 | 必须用紧凑 JSON 且以 `content=` 发送原文；用 `json=` 会因序列化差异导致验签失败 | ✅ 通过 |
| 空值头处理 | `x-vin` 与 `authorization` 为空时**跳过**（发空的 `Bearer ` 会被拒）；其余白名单头即使为空也写入 | ✅ 通过 |
| 签名密钥 | `ZEEKR_PROD_SECRET` —— **提取器给的候选不对**（`079025`），实际用的是另一组已验证常量 | ✅ 已定案 |

**判定方法**（不必重新登录）：登录成功后令牌落盘 `server/data/session.json`，
之后"哪个路径对 / 哪个字段名对 / 哪组密钥对"都能用**换一个候选重发同一条 GET** 问网关，
零短信成本。

- 返回 `079025 Signature authentication failed` → 签名串构造或**密钥**有误
- 返回 `079025 Decrypt X-VIN failed` → **同一个错误码**，但问题在 X-VIN 加密（见第二节）
- 返回 `079001 接口未被授权` → 签名已通过，问题在令牌代际或账号权限
- 返回 `000000` + 数据 → ✅ 通过

> ⚠️ `079025` 是**复用错误码**。日志已按 `msg` 分流；只打码不打 msg 会把排查方向带偏
> （本项目踩过：一直误判成签名问题，实际是 X-VIN 密钥不对）。

## 四、接口的路径定案与遗留

| 接口 | 结论 | 状态 |
|---|---|---|
| 车辆列表 | `GET /ms-app-bff/api/v3.0/veh/vehicle-list?needSharedCar=true`（**不带 X-VIN**） | ✅ 通过 |
| 车况 | `GET /ms-vehicle-status/api/v1.0/vehicle/status/latest` | ✅ 通过 |
| 充电计划 | `GET /ms-charge-manage/api/v1.0/charge/getChargingPlanNew`（**v2.0 是 404**） | ✅ 通过 |
| 行程 | `POST /ms-vehicle-trail/api/v1.0/journalLog/trip/listForPage`；`startTime`/`endTime` 必须是**数字时间戳**（传字符串一律 `000002`），列表在信封的 **`data`** 键下（不是 `list`） | ⚠️ 修完仍 `total=0` |
| 权限包 | `GET /ms-app-bff/api/1.0/permissions?tspPlatform=5`，**必须带 X-VIN**（缺了 `079001`） | ✅ 通过（返回 21 项） |
| 能力集 | `ms-vehicle-capability-set` 在 snc-tsp-api 是**网关级 404**（`00A01 / bizName: API Gateway`；网关、版本号、GET/POST、多 host 全试过）→ 路由未注册，已被权限包取代，**不再调用** | ❌ 服务不在本网关 |

**行程 `total=0`**：参数修对后仍返回 0（7/30/90 天都一样），疑与 `journalLog/onOff` 开关有关。不臆造数据。

### 权限包 `tspPlatform` 取值（枚举实测，非猜测）

`/ms-app-bff/api/1.0/permissions` 的必填参数。2026-10-16 让网关自己回答：

| 取值 | 网关回答 |
|---|---|
| 非数字（`ZEEKR` 等） | `000002 param check failed` —— 参数校验就挂了 |
| `1` / `2` / `3` | `037021 平台类型未定义` |
| `4` | `000000 ok`，但 `data` 为**空数组** |
| `5` / `7` / `8` / `21`…`27` | `000000 ok`，返回该车 **21 项权限**（内容一致） |

⇒ 本项目取 `5`，可用 `.env` 的 `ZEEKR_TSP_PLATFORM` 覆盖。

### 权限包 ≠ 硬件能力（这条边界别踩）

权限包返回的是**服务 / 功能 ID**（`charge-manage` / `vehicle-defence` /
`owner-vehicle-trail` …），**不是**胎压 / 空调 / 车窗这类硬件能力。

因此代码里只允许隐藏**服务类**功能；硬件能力一个都不写进映射表 ——
前端对缺失键返回"照常显示"。拿权限接口去隐藏硬件按钮就是臆测，
宁可多显示一个按了没反应的按钮，也不能把真车有的功能藏起来。
（`tests/test_adapter_shape.py` 有安全断言守着这条边界。）

## 五、车控指令 —— 完全未验证

车控需要抓包：官方 App 的车控走 **GRIC** 体系
（`gric-zhf-api.geely.com` + `GEELYCNCH001M0001` + `x-signature` 2.1），
与 ZEEKR 三网关**平行**，密钥静态不可得。

| 指令 | serviceId | 状态 |
|---|---|---|
| 锁车 | `RDL` | ⬜ 待验证 |
| 解锁 | `RDU` | ⬜ 待验证 |
| 开/关空调 | `ZAF` + `AC` 参数 | ⬜ 待验证 |
| 闪灯 | `RHL` + `rhl=light-flash` | ⬜ 待验证 |
| 鸣笛 | `RHL` + `rhl=light-horn` | ⬜ 待验证 |
| 开始/结束充电 | `RCS` | ⬜ 待验证 |

**注意**：指令返回「已提交」只代表网关收下，**不代表车端已执行**。
`GET /api/vehicle/command/result?id=<commandId>` 是消除假成功的唯一手段
（三态 `pending` / `done` / `failed`，解析不出时一律 `pending`）。

### 5.1 两把锁（别只开一把）

下发一条车控指令，需要**同时**满足：

| 锁 | 位置 | 默认 |
|---|---|---|
| 客户端总开关 | 网页：设置 → 车辆控制 → 「允许下发控制指令」<br>App：设置 → 车辆控制（同一开关语义，`SettingsStore.commandsEnabled`） | **关** |
| 服务端开关 | `.env` 的 `ALLOW_COMMANDS=true`，改后**必须重启服务** | `false` |

客户端开关关着时，两个客户端的车控按钮一律置灰、标题旁标「已禁用」，并给出一行
「在设置中开启…」的说明 —— 按钮**不隐藏**（隐藏会让人以为功能丢了），
网页与 App 行为已对齐（网页侧用 Node 无头渲染逐条验证过，未入库为回归脚本）。
服务端开关状态在网页「服务连接 → 服务端车控」、App「诊断 → 服务端车控」里都能看到。

> 社区实测发现部分命令存在两套参数（如车窗 `RWS` + 小写 target vs `RWS_2` + 大写 `TARGET`），
> 本项目采用 `RWS` 小写版本，若无效可参考 `borconi/openzeekr` 的 A/B 对照表调整。
