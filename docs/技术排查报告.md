## 2. P0 与 P1

### 2.1 【P0，已复核】预览页：瞬时故障后，演示金额仍按真实样式显示

**位置**：`preview/index.html:5690-5692`（无条件覆写）、`:3810`（角标只认 mode）、`:5986-5998`（恢复 live 不清演示数据）、`:5728` / `:5741`（MOCK 金额来源）、`:3852`（金额渲染）

**机制**（三段拼起来才成立，所以第一轮的"加角标"改法没堵住）：

```js
// ① 离线态进充电页：无条件用演示数据覆写，即使 state.charge 里已有真实流水
if (state.mode === 'mock' || state.mode === 'offline') { applyMockCharges(); return true; }

// ② 角标只看模式，不看数据来源
const demo = state.mode !== 'live';

// ③ 后端恢复：clearLoadedKeys() 只清两个 Set，不动 state.charge / chargeMonths
if (state.mode === 'offline') clearLoadedKeys();
state.mode = 'live';
syncModeBadge();
render();          // ← 此刻 render 的是 MOCK 流水，demo 已变 false
```

**复现**：live 下充电页有真实流水 → 后端短暂不可达（auth 仍成功、`/api/vehicle/status` 失败）→ 进充电页（被演示数据覆盖）→ 后端恢复、任一健康检查成功 → `mode='live'` + `render()`。屏幕上就是「演示金额 + 无角标」，而且此后只要用户停在这一页、不切 tab 触发 `ensureTabData`，就不会重新取数。

**影响**：演示金额是 `mockCharge` 里的固定值，与真金额同字号同颜色；用户会把它当成自己的账。这是第一轮 P0 的**残存形态**，`5b00745` 只堵住了 `if (!state.status) seedMock()` 那一半（`:5986`）。

**修复建议**：给充电/行程数据打来源标记（`state.chargeSource = 'mock' | 'live'`），角标按来源渲染；`applyMockCharges()` 只在 `!state.charge` 时写；恢复 live 时清掉 mock 派生的 `charge/chargeMonths/energy` 并强制重取当前 tab。

### 2.2 【P1】服务端：例行同步会把已识别的电量/时长/结束时间抹成 NULL

**位置**：`server/app/core/store.py:312-322`（第一轮 §4.1#1，`1073414` 没碰这段）

```sql
ON CONFLICT(session_id) DO UPDATE SET
    start_ts = excluded.start_ts, end_ts = excluded.end_ts,
    duration_min = excluded.duration_min, energy_kwh = excluded.energy_kwh,
    charge_type = excluded.charge_type,
    station_name = COALESCE(charge_sessions.station_name, excluded.station_name),
    amount = COALESCE(charge_sessions.amount, excluded.amount)
```

只有 `station_name` / `amount` / `amount_source` 用了 `COALESCE`，4 个数值列仍是**无条件覆盖**。上游确实会缺字段（`live_client.py:1930-2009` 在 `power`/`chargedTime` 缺失时明确产出 `None`）。

**实测**：同 `sessionId` 先落 `energy=42.5 / min=60 / end=2026-10-16 23:10`，再同步一次、上游这三项为 NULL → 读回 **全 None**（不可逆）。随后 `session_months` 变成 `{'count':1,'kwh':0.0,'minutes':0}`，预览页 `:3852` 的 `fmt(c.totalKwh, 1)` 把它渲染成「**0.0 度**」——这正是铁律②禁止的编造数字。

**修复建议**：4 个数值列改 `CASE WHEN excluded.x IS NULL THEN charge_sessions.x ELSE excluded.x END`；`charge_type` 再加 `AND excluded.charge_type <> 'unknown'`；补「二次同步上游 NULL 不覆盖」用例。

### 2.3 【P1】预览页：客户端超时比服务端上游超时还短，车控/OCR/同步会被前端先掐断

**位置**：`preview/index.html:2582`（`withTimeout(15000)`）、`:5036`（`withTimeout(12000)`） ↔ `server/app/adapters/live_client.py:103`（`httpx.Timeout(20.0, connect=10.0)`）、`server/app/adapters/vision_ocr.py:329`（`httpx.AsyncClient(timeout=60.0)`）

三条被影响的链路：`POST /api/charges/receipts/ocr`（服务端允许 60 秒）、`POST /api/charges/sync`、`POST /api/vehicle/command`（走 20 秒的 `live_client`）。

**后果**：① OCR 15 秒被前端 abort，服务端可能仍在算/已入库，用户只看到「请求超时（15 秒无响应）」；② 充电同步被掐断，而 `runChargeSync` 的 `catch` 是静默的（`:5664-5668`）⇒ 页面一直「未同步」且无任何提示；③ 车控 15 秒 < 20 秒，指令可能已被受理而前端弹「锁车失败：…请求超时」——对安全动作这是**假阴性**。

**修复建议**：按接口分级：OCR 至少 70 秒、同步/车控 30 秒以上、普通读接口保持 10–15 秒；或把服务端自身上游超时压到客户端之下，保证"服务端先说话"。
